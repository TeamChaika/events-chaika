# Чайка · События

Webapp для продажи билетов, управления мероприятиями и проверки QR на входе. Первый экран — анимированная афиша «Ночь красной луны» по предоставленному референсу. Цена первого события: **5 000 ₽**. Дата 31 октября взята из афиши; время 20:00 и вместимость 200 — редактируемые тестовые значения.

## Запуск

Node.js 22.23+ (используется встроенный SQLite).

```sh
npm ci
cp .env.example .env
chmod 600 .env
npm run dev
```

- Сайт: http://localhost:5173
- Админка: http://localhost:5173/admin
- Контроль входа: http://localhost:5173/checkin
- Мобильный предпросмотр для разработки: http://localhost:5173/qa-preview.html

В `.env` включён **локальный демо-режим**: вход в панели без пароля и явная кнопка имитации оплаты. Настоящие платежи и сообщения не отправляются. Сервер разработки слушает только loopback. Не выставляйте dev-сервер наружу. В production демо-режим запрещён при запуске.

## Что работает

- Анимированные луна, туман, летучие мыши; кнопка паузы, поддержка reduced motion; мобильная версия.
- Имя, фамилия, телефон, почта, количество билетов. Расчёт стоимости на сервере, фиксированная цена в заказе.
- Сохранение заказов и резервов в SQLite; дедупликация повторного запроса; ограничение вместимости.
- QRM: проверка терминала, создание СБП, защищённая ссылка callback, GET/SSE-сверка статуса и суммы. Неподтверждённый webhook не выпускает билеты.
- Один отдельный случайный QR на каждый билет. Страница каждого билета и печать/сохранение в PDF через браузер.
- Админка: создание/редактирование событий, загрузка своей афиши/фона, стоимость, вместимость, дата, время, площадка, описание, дресс-код, публикация, остановка продаж.
- Заказы, поиск по гостям, повторная сверка оплаты, очередь доставки и статусы.
- Бесплатные приглашения и продажа за наличные с явным подтверждением получения денег сотрудником.
- Отдельная роль контролёра: проверка камерой через ZXing и по ссылке/полному коду, атомарный однократный проход.
- Telegram Bot API, SMTP-почта с QR-вложениями, СМС через SMS.RU. Успешная передача сервису не объявляется доказанной доставкой на устройство.

## Подключение к рабочим сервисам

Секреты вводятся только в серверную `.env` или переменные хостинга. Шаблон — `.env.example`. Ключи из других проектов не копировались.

1. Установите публичный HTTPS `APP_ORIGIN` и `DEMO_MODE=false`.
2. Задайте разные `ADMIN_PASSWORD` и `SCANNER_PASSWORD`, каждый не короче 16 символов.
3. QRM: сначала нужная тестовая среда `QRM_MODE=sandbox` + `QRM_API_KEY`. Для рабочего терминала: `QRM_MODE=live`, `QRM_LIVE_API_KEY`, `QRM_API_BASE_URL`, `QRM_EXPECTED_MERCHANT_ID`. Терминал проверяется перед созданием платежа. Публичный callback формируется автоматически. Подробнее: [docs/QRM.md](docs/QRM.md).
4. Telegram: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`. Почта: SMTP-параметры и `MAIL_FROM`. СМС: `SMS_RU_API_ID`.
5. Когда каналы готовы, установите `DELIVERY_ENABLED=true`. Доставка по тестовым заказам всё равно запрещена. Старые задания `disabled` можно повторить из админки после настройки. При неизвестном результате сначала проверяется сервис, затем сотрудник подтверждает повтор.
6. Перед открытием продаж замените информационный текст о конфиденциальности реквизитами организатора и рабочими условиями покупки/возврата. Проверьте схему чеков в QRM; текущий код передаёт номенклатуру, но не подтверждает настройки вашей кассы.

**Сейчас подтверждены локальная работа и fixture-тесты. Реальные QRM-платежи, получение Telegram, SMTP/СМС и камера физического телефона не проверялись: ключи и публичный HTTPS ещё не заданы.**

## Развёртывание

```sh
npm run build
npm start
```

Один процесс Node обслуживает frontend и API. Есть Dockerfile. Нужны постоянный диск для `data/`, резервное копирование SQLite и HTTPS reverse proxy. За единственным доверенным reverse proxy задайте `TRUST_PROXY_HOPS=1`; иначе оставьте `0`. Production запуск намеренно прекращается без HTTPS, паролей или при включённом демо.

Это реализация для одного экземпляра сервера. При нескольких репликах нужна общая БД и распределённая очередь. SQLite-файл не должен быть на эфемерном диске. Камере нужен HTTPS (либо localhost) и разрешение браузера. Вход работает онлайн; офлайн-проход не поддерживается. Webapp открывается на телефоне и имеет manifest; нативное приложение не нужно.

После публикации нужно проверить реальную цепочку: покупка → подтверждение QRM → отдельные билеты → уведомления → сканирование на телефоне. Публикация не выполнялась.
