## Предпросмотр

`http://localhost:8802/?event=odisseya` — отдельная локальная база `data/odisseya-preview.sqlite`, DEMO, без отправки сообщений и реального списания. Запуск: `node .deployment/odisseya-preview.mjs` после `npm run build`. В локальной базе есть демонстрационный заказ на два места. Производственные данные не использовались.

Файл `.deployment/odisseya-draft.json` содержит данные для создания мероприятия через существующий административный API, с закрытыми продажами и выключенной публикацией. Включённая публикация в локальной базе служит только предпросмотру. `layout=odisseya` выбирает самостоятельную страницу и оформление билета; `payment_account=livadia` выбирает отдельный терминал. Боевой ID при создании через API будет новым; клиент использует `/?event=<id>`.

## Терминал

Ввод ключа: **Админка → Подключения → СБП · Ливадия → Проверить и сохранить**. Сервер проверяет ключ методом check-api-key без создания платежа, показывает получателя и закрепляет merchant_id. Ключ не возвращается клиенту; хранится в таблице payment_accounts в AES-256-GCM с отдельным серверным QRM_SETTINGS_ENCRYPTION_KEY (32 случайных байта base64). Этот ключ шифрования должен сохраняться между деплоями и храниться в защищённых runtime-переменных хостинга; его потеря делает сохранённые настройки недоступными. Таблица включена в существующую защиту PostgreSQL. Доступ только администраторам, запись фиксируется в аудите без секрета.

Основной терминал по-прежнему читает существующие QRM_* из окружения. Для Livadia настройки в БД имеют приоритет над QRM_LIVADIA_*; без обоих вариантов оплата закрыта. Смена merchant_id через форму запрещена, чтобы не потерять доступ к старым платежам. У заказа сохраняется собственный payment_account. Файл .env.qrm-livadia.local больше не нужен для пользовательского ввода через админку.

Сохранение ключа не открывает продажи. После проверки получателя и чеков включить продажи в настройках мероприятия. Проверка ключа сама по себе не подтверждает оплату и фискализацию.

Официальная спецификация проверена 22 октября 2026: https://docs.qrmanager.ru/static/merged_swagger-2.json. Используются существующие check-api-key, operations/qr-code и SSE qr-status; единицы сумм и логика сверки сохранены.

## Проверено локально

Сборка; 156 успешных тестов, 2 штатно пропущенных PostgreSQL-теста. Проверены отсутствие подмены терминалов, блокировка без ключа, неизменность терминала у заказа, повтор запроса без второго платежа, выпуск билетов после сверки суммы, сохранение новых полей при старых клиентах, СМС с нужным названием площадки. Проверены браузерный макет на 1280 и 390 px, форма и демонстрационный билет на двух гостей. HTML страницы отдаёт название и афишу выбранного события для ссылок.

Изображения `odisseya-world*.jpg` созданы на основе предоставленной афиши без встроенных надписей; заголовки, дата, меню и кнопки — HTML. Исходная афиша сохранена отдельно для миниатюры заказа и ссылки-превью.

Миграция на рабочем PostgreSQL и создание мероприятия через административный API проверены. Реальная оплата и фискализация ещё не проверены. Для открытия продаж нужен подтверждённый терминал; возрастное ограничение нужно уточнить до начала продаж. Рекламная подписка «Гастро Двора» в форме «Одиссеи» не показывается.
