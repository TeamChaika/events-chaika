# Ступенчатая цена билетов

Цена хранится в копейках. Поле `events.price_tiers` содержит JSON-массив с возрастающими границами и ценами. Последняя граница — `null`. Отсутствие политики сохраняет прежнюю фиксированную цену.

Для «Ночи красной луны»:

```json
[
  { "up_to": 50, "price": 500000 },
  { "up_to": 150, "price": 800000 },
  { "up_to": null, "price": 1000000 }
]
```

Общий лимит вместимости независим от ценовых ступеней. Для события согласовано 300 гостей.

- Квоты учитывают количество билетов, а не заказов. Обычные продажи до включения политики занимают первые места; их суммы не изменяются.
- Оплаченные заказы и резервы `creating`, `pending`, `unknown` занимают места в своих ступенях. Тестовые, аннулированные, пригласительные и sandbox-заказы не расходуют ценовые квоты. В изолированной demo-среде учитываются только demo-заказы.
- `expired`, `cancelled`, `failed` освобождают свои ценовые места. Само истечение локального таймера не освобождает неизвестный банковский платёж.
- `GET /api/events/:id/quote?quantity=N` возвращает строки и итог. Форма передаёт `expected_total`. Сервер под транзакционной блокировкой заново вычисляет сумму. При её изменении возвращается `409 PRICE_CHANGED`, заказ и банковская операция не создаются. Гость видит обновлённую сумму и подтверждает её повторно.
- `orders.price_breakdown` фиксируется при создании заказа. Пересечение ступени создаёт несколько ценовых строк, которые передаются в номенклатуру QRM. `unit_price` сохранён для совместимости и отражает первую строку; итог всегда берётся из `total`, полная разбивка — из `price_breakdown`.
- Повтор с тем же ключом идемпотентности возвращает исходный заказ с исходной ценой. Неопределённый результат создания платежа не вызывает повторного банковского POST.
- Если подтверждение приходит после освобождения резерва и его ценовые места уже заняты, заказ получает `paid_review` и уведомление администратору. Деньги не пересчитываются, повторно не списываются; до сверки билет не выпускается.
- В админке: «Мероприятия» → «Билеты и цены». В каждой существующей ступени задаются полное количество билетов (включая уже проданные/резервы) и цена для новых заказов. Сумма количеств задаёт общий лимит гостей; цены ступеней возрастают. Форма показывает оплаченные билеты и резервы по ступеням, а не продажи по фактическим историческим ценам. Пригласительные расходуют вместимость зала, но не ценовые квоты.
- `GET /api/admin/events/:id/pricing` возвращает текущие количества, цены, занятые квоты и ревизию настроек. `PUT` на тот же адрес принимает `{ revision, tiers: [{ quantity, price }] }`, где цена в копейках. Оба метода доступны только администратору. Нельзя уменьшить ступень ниже оплаченного/зарезервированного количества или общий лимит ниже занятых мест. Изменение числа/порядка ступеней в этой форме не поддерживается.
- Сохранение настроек и резервирование покупки используют одну транзакционную блокировку. Устаревшая ревизия возвращает `409 PRICING_STALE`; новые резервы повторно проверяются при сохранении. Изменение квоты/цены фиксируется в журнале аудита. Перед изменением старые заказы без разбивки получают привязку к прежним ступеням с сохранением их реальной цены, суммы и статуса. Уже существующие разбивки, счета и билеты не пересчитываются.
- Обычная форма редактирования события сохраняет действующие ступени, базовую цену и вместимость. Менять их следует через «Билеты и цены». Отключение или замена структуры используемой политики через общий endpoint запрещены. Поздняя оплата проверяет в том числе квоту последней ступени.

Активация выполняется через существующий авторизованный `PUT /api/admin/events/:id` с полным набором полей события и `price_tiers`. Сначала развернуть новую версию приложения и дождаться успешного запуска всех экземпляров, затем активировать политику. Старые версии приложения не поддерживают смешанные цены: откат к ним после активации требует закрыть продажи и подготовить совместимое исправление.

Проверки: API-тесты для границ 50/150, исторических продаж, исключений, идемпотентности, устаревшего расчёта, освобождения резерва, позднего платежа и наличных. Редактор проверяется на изменение цен/квот после продаж, сохранение сумм старых счетов, конфликт двух редакторов, покупку одновременно с уменьшением квоты, ограничения доступа и вместимость с пригласительными. Отдельный PostgreSQL-тест создаёт конкурентные заказы в двух экземплярах приложения. QRM проверяется локальным mock, без реального списания.

## Промокоды

В «Билеты и цены» администратор задаёт скидку в рублях или процентах на билет. Один заказ принимает один код. Новые настройки `limit_scope` (`orders` / `tickets`), `max_uses` (положительный лимит или `null`), `starts_at` и `ends_at` (ISO-время или `null`) сохраняются вместе с кодом. Старые коды остаются безлимитными. Форма показывает даты в UTC+3: начало включительно, окончание исключительно; пустая дата не ограничивает срок.

- По заказам: заказ на любое допустимое количество гостей расходует одно использование, скидка применяется ко всем билетам.
- По билетам: каждое место со скидкой расходует одно использование. Если из пяти билетов лимита хватает на два, первые два по сохранённой ценовой разбивке получают скидку, три остаются по полной цене. Форма покупки явно показывает это до оплаты.
- Одноразовый код — лимит 1 в выбранных единицах. Лимит общий для мероприятия, не на покупателя.
- Расчёт цены не расходует лимит. Создание заказа резервирует его под общей транзакционной блокировкой. `creating`, `pending`, `unknown` держат резерв; подтверждённые `failed`, `cancelled`, `expired` освобождают. Для неизвестного банковского платежа одного истечения таймера недостаточно.
- `paid` и `paid_review` считаются использованными, в том числе при последующем аннулировании оплаченного заказа. Тестовые и пригласительные не расходуют лимит. `promo_usage` в ответе административного pricing API содержит оплаченные и зарезервированные заказы и билеты по каждому коду.
- История считается по `discount_snapshot` заказа: удаление/повторное добавление того же кода не обнуляет счётчик. Изменение единиц пересчитывает историю в новых единицах. Уменьшение лимита ниже уже использованного не меняет заказы, а блокирует новые применения.
- Сумма, число билетов со скидкой и правило фиксируются в заказе. Отключение/истечение кода не отменяет уже оформленную оплату. Поздняя оплата после освобождения и повторного использования лимита переводится в `paid_review`, без автоматического выпуска билетов.

При выкладке дождаться обновления всех экземпляров приложения до включения ограниченных кодов. Откат на старую версию после включения лимитов не поддерживается: старый код не проверяет эти ограничения.
